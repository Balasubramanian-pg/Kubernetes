## What it is

Logs are records of events generated by operating systems, applications, services, and infrastructure components. They help engineers understand what happened, when it happened, and why a process or application may have failed.

Linux systems commonly expose logs through files stored under `/var/log` and through the systemd journal, which can be queried using `journalctl`.

The primary commands are:

- `tail`: Display the last lines of a file.
- `tail -f`: Follow a file as new log entries are appended.
- `tail -F`: Follow a log by filename and attempt to recover when the file is rotated or recreated.
- `less`: Inspect large log files interactively.
- `grep`: Filter log entries by text or patterns.
- `journalctl`: Query logs collected by systemd-journald.
- `dmesg`: Display kernel ring-buffer messages, subject to system permissions and configuration.
- `systemctl status`: Inspect a systemd service and view recent status information, often including recent log messages.

For data engineers, log analysis is essential for troubleshooting failed ETL pipelines, database connectivity issues, resource exhaustion, Docker container failures, and Kubernetes workload restarts.

## Key points

- **Application logs versus system logs:** Application logs describe events within an application, such as pipeline execution and database errors. System logs record operating system, service, kernel, and infrastructure events. Both may be necessary to identify the root cause of a failure.

- **Log levels:** Common severity levels include `DEBUG`, `INFO`, `WARN` or `WARNING`, `ERROR`, and `FATAL` or `CRITICAL`. Exact names and meanings depend on the application and logging framework.

- **Reading the end of a file:** `tail -n 100 application.log` displays the last 100 lines. This is useful when investigating recent failures without printing an entire file.

- **Following a live log:** `tail -f application.log` displays new data as it is appended. Press `Ctrl+C` to stop following. This is useful when reproducing an issue while observing application output.

- **Handling log rotation:** Log rotation renames, compresses, or replaces log files to control disk usage. `tail -f` follows the existing file descriptor and may continue reading the old file after rotation. `tail -F` follows the filename and retries when the file is replaced or recreated.

- **Understanding the systemd journal:** `journalctl` queries logs collected by `systemd-journald`. Depending on the system configuration, journal data may be stored persistently or only for the current boot.

- **Filtering by service:** `journalctl -u nginx` displays journal entries associated with the `nginx` unit. Replace `nginx` with the actual service name on the machine.

- **Filtering by time:** Options such as `--since` and `--until` narrow the log window. Specify clear timestamps when investigating an incident so unrelated events do not obscure the failure.

- **Following journal entries live:** `journalctl -f` follows new journal messages. Combine it with `-u SERVICE_NAME` to monitor one service.

- **Investigating the current boot:** `journalctl -b` shows journal entries from the current boot. `journalctl -b -1` requests entries from the previous boot, if those entries are available.

- **Kernel logs:** `dmesg` can reveal hardware, driver, filesystem, and memory-related messages. Access to some messages may be restricted by system security settings.

- **Service status versus service logs:** `systemctl status SERVICE_NAME` provides the service's current state and often recent journal entries. Use `journalctl -u SERVICE_NAME` to perform a more focused log investigation.

- **Timestamps and time zones:** Compare timestamps across applications and infrastructure. Different time zones, clock drift, and inconsistent timestamp formats can make events appear out of sequence.

- **Correlation IDs:** Distributed applications may attach request IDs, job IDs, trace IDs, or correlation IDs to log entries. Searching by a shared identifier helps connect events across multiple services.

- **Structured logging:** JSON logs with fields such as timestamp, severity, service name, job ID, and error message are easier to filter and analyze consistently than unstructured text.

- **Logs are not metrics or traces:** Logs record individual events, metrics summarize numerical measurements over time, and traces follow requests across distributed components. They complement each other during troubleshooting.

- **Container logs:** `docker logs` retrieves the logs exposed by a container's configured logging mechanism. Output availability depends on the application's logging behavior and Docker's logging driver.

- **Kubernetes logs:** `kubectl logs` retrieves logs from a container in a Pod. For restarted containers, `kubectl logs --previous` can retrieve logs from the previous container instance when available.

- **Logs can expose sensitive data:** Avoid logging passwords, access tokens, connection strings, and unnecessary personal information. Restrict access and follow appropriate retention policies.

- **Disk usage matters:** Unbounded logs can consume filesystem space and cause application failures. Use log rotation, retention limits, and centralized logging where appropriate.

## Commands / manifests

```bash
# 1. Inspect available system logs
ls -lah /var/log

# 2. Read the last 50 lines of a log
tail -n 50 /var/log/syslog

# On distributions that use /var/log/messages instead
tail -n 50 /var/log/messages

# 3. Follow a log as new lines are appended
tail -f application.log

# 4. Follow a log across rotation or recreation
tail -F application.log

# 5. Search for errors
grep -in 'error' application.log

# 6. Follow a log and filter matching entries
tail -F application.log | grep --line-buffered -i 'error'

# 7. Inspect a systemd service
systemctl status nginx

# 8. View all available journal entries for a service
journalctl -u nginx

# 9. Display the most recent 100 journal entries
journalctl -n 100

# 10. Follow journal entries in real time
journalctl -f

# 11. Follow logs for a specific service
journalctl -u nginx -f

# 12. Filter journal entries by time
journalctl --since "1 hour ago"
journalctl --since "2026-10-24 10:00:00" \
           --until "2026-10-24 11:00:00"

# 13. Inspect logs from the current boot
journalctl -b

# 14. Inspect previous boot logs, if retained
journalctl -b -1

# 15. Show warnings and more severe journal entries
journalctl -p warning

# 16. Inspect kernel messages
dmesg --level=err,warn

# 17. Check filesystem capacity
df -h

# 18. Identify large log files
du -sh /var/log
find /var/log -type f -size +100M -print 2>/dev/null
```

The exact files under `/var/log` vary by Linux distribution. For example, Debian and Ubuntu systems commonly use `/var/log/syslog`, while some other distributions use `/var/log/messages`. Systemd-based machines may rely heavily on the journal.

### Docker logs

```bash
# Display a container's logs
docker logs CONTAINER_NAME

# Display the last 100 lines
docker logs --tail 100 CONTAINER_NAME

# Follow logs in real time
docker logs -f CONTAINER_NAME

# Display timestamps
docker logs -t CONTAINER_NAME

# Show logs generated within a recent time window
docker logs --since 30m CONTAINER_NAME

# Follow logs with timestamps and limit initial output
docker logs --tail 50 -f -t CONTAINER_NAME
```

Replace `CONTAINER_NAME` with the actual container name or ID. Docker log availability depends on the configured logging driver and whether the application writes to standard output and standard error.

### Kubernetes logs

```bash
# List Pods in the current namespace
kubectl get pods

# Display logs from a Pod
kubectl logs POD_NAME

# Follow logs in real time
kubectl logs -f POD_NAME

# Display the most recent 100 lines
kubectl logs --tail=100 POD_NAME

# Retrieve logs from a specific container in a multi-container Pod
kubectl logs POD_NAME -c CONTAINER_NAME

# Inspect logs from a previous container instance
kubectl logs POD_NAME --previous

# Retrieve logs from Pods selected by a label
kubectl logs -l app=my-app --all-containers=true --tail=100

# Inspect Pod events and restart information
kubectl describe pod POD_NAME

# Check recent cluster events
kubectl get events --sort-by=.metadata.creationTimestamp
```

Use `-n NAMESPACE` when the workload is not in the current namespace. Previous-container logs are available only when the runtime still retains them. For distributed workloads, correlate Pod logs with events, deployment history, application metrics, and tracing data.

### Hands-on log investigation

```bash
# Create a sample application log
cat > application.log <<'EOF'
2026-10-24T10:00:00Z INFO Pipeline started
2026-10-24T10:00:02Z INFO Source connection established
2026-10-24T10:00:05Z WARN Retry attempt 1
2026-10-24T10:00:10Z ERROR Database connection timeout
2026-10-24T10:00:11Z INFO Retrying connection
2026-10-24T10:00:15Z ERROR Database authentication failed
EOF

# Display the latest entries
tail -n 3 application.log

# Find errors with line numbers
grep -in 'ERROR' application.log

# Count errors
grep -ic 'ERROR' application.log

# Extract errors into a separate report
grep -i 'ERROR' application.log > error-report.log

# Follow the file in another terminal
tail -F application.log

# Append a new entry from this terminal
echo "2026-10-24T10:01:00Z INFO Pipeline recovered" >> application.log

# Inspect the resulting log
tail -n 5 application.log

# Remove practice files
rm -f application.log error-report.log
```

## Common failures & fixes

- **`tail: cannot open ... No such file or directory`:** Verify the path and filename with `pwd` and `ls`. The application may be writing logs to another directory or sending them to standard output instead of a file.

- **`Permission denied` when reading logs:** Check file ownership and permissions. Use an authorized account or approved elevated access when necessary. Avoid changing system log permissions broadly.

- **`tail -f` stops showing new entries after log rotation:** The original file may have been renamed or replaced. Use `tail -F` to follow the filename and retry when the file changes.

- **`journalctl` returns no entries:** Confirm that the system uses systemd, check the service name, time filter, permissions, and journal retention settings. Some systems use other logging services.

- **`journalctl -u SERVICE_NAME` shows nothing:** Verify the exact unit name with `systemctl list-units --type=service --all`. The application may log to a file, another service, or a container runtime rather than the expected unit.

- **Previous boot logs are missing:** Journald may be configured for volatile storage, or older entries may have been removed by retention limits. Configure persistent journal storage if historical boot logs are required.

- **Logs contain too much irrelevant information:** Narrow the time range, service, severity, or request identifier. Use `grep`, `journalctl --since`, and `journalctl -p` to filter the data.

- **An error is missing from `docker logs`:** The application may write to a file inside the container rather than standard output or standard error. Inspect the application's logging configuration and the Docker logging driver.

- **Kubernetes logs disappear after a Pod restart:** Try `kubectl logs POD_NAME --previous` if the previous container instance is still available. For longer-term retention, use centralized logging rather than relying exclusively on Pod-local logs.

- **A Pod is repeatedly restarting:** Check `kubectl describe pod POD_NAME`, current logs, previous-container logs, and recent events. Investigate exit codes, failed health probes, resource limits, configuration errors, and dependency failures.

- **Log timestamps appear out of order:** Check time zones, system clock synchronization, timestamp formats, and whether events are generated by different hosts. Prefer consistent UTC timestamps in distributed systems.

- **Log files consume too much disk space:** Inspect usage with `du -sh /var/log` and `df -h`. Configure log rotation and retention, and investigate applications producing excessive output. Do not delete active logs blindly, since running processes may keep deleted files open.

- **A log-following pipeline delays output:** Tools such as `grep` may buffer output when writing to a pipe. For GNU `grep`, use `--line-buffered` when following live logs and filtering matching lines.

- **Sensitive information appears in logs:** Restrict access, remove inappropriate logging, and rotate exposed credentials where necessary. Apply appropriate retention and redaction controls.
